## 目标
在不改动应用源码或版本号的前提下，基于当前 `main`（比 `origin/main` 超前 1 个提交、工作区干净）验证项目健康状态，并生成当前 Windows x64 的可分发安装包。

当前发布版本由 `package.json:2` 和 `src-tauri/tauri.conf.json:3` 一致定义为 `3.20.0`；Windows 实际发布流程以 WiX MSI 为准，而不是 README 中已过时的 NSIS 示例。

## 执行步骤
1. **确认本机构建前提**：检查 Node、pnpm、Rust、Cargo 及 Windows 打包工具是否可用，并确认依赖目录与锁文件可用于可复现构建。不会安装或升级任何全局工具。
2. **执行与 CI 对齐的质量检查**：依次运行：
   - `pnpm typecheck`
   - `pnpm format:check`
   - `pnpm test:unit`
   - `cargo fmt --check --manifest-path src-tauri/Cargo.toml`
   - `cargo clippy --manifest-path src-tauri/Cargo.toml -- -D warnings`
   - `cargo test --manifest-path src-tauri/Cargo.toml`

   如果检查失败，会区分新增问题与项目已知基线；只有在未发现实际阻塞问题时才继续打包。
3. **构建 Windows x64 MSI**：运行 `pnpm tauri build --bundles msi`。该命令会通过 `src-tauri/tauri.conf.json:9` 自动构建前端，并输出便携式 EXE 和 WiX MSI。
4. **验证产物**：确认预期的 `src-tauri/target/release/cc-switch-pd.exe` 和 `src-tauri/target/release/bundle/msi/*.msi` 已生成，记录文件名、大小和版本信息；再次检查 Git 工作区，确保构建未引入源码改动。
5. **如更新签名缺失**：因为 `src-tauri/tauri.conf.json:38` 要求生成自动更新签名，构建可能在安装包已成功生成后因未配置 `TAURI_SIGNING_PRIVATE_KEY` 返回非零。我会仅在 MSI 和 EXE 实际生成且日志明确指向签名缺失时，将其报告为“未签名的本地构建完成”；不会绕过、伪造或修改签名配置。

## 产出与边界
- 产出是当前主机可用的 Windows x64 MSI 安装包（以及构建过程生成的可执行文件），不会创建 Git tag、GitHub Release、提交或推送。
- macOS 签名/公证和 Linux 包须在对应原生环境与发布凭据下构建，本次不会尝试跨平台打包。
- 构建目录中的二进制产物属于本地生成物，不会加入版本控制。
